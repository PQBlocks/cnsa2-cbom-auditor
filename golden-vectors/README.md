# golden-vectors — CNSA 2.0 PKI auditor test instances

These are the fixed test instances for **pqblocks-cnsa-evidence**. They are real X.509
certificates and real SubjectPublicKeyInfo files generated by the locally installed OpenSSL
3.6.5 (not hand-written fixtures), covering every algorithm family the product must classify.

## Why these vectors exist

The product's correctness claim is: *for a given certificate, the CBOM verdict matches the
FIPS table for that OID*. That claim is only testable against certificates whose parameters are
known-good independently of the product. So the vectors are generated by OpenSSL and their
expected classification is derived by `derive-expected.mjs` from `openssl x509 -text` output —
never from the product's classifier (R15: external oracle primacy).

## Files

| file | purpose |
|---|---|
| `generate.sh` | regenerates `certs/` and `spki/` with the local OpenSSL |
| `derive-expected.mjs` | independent oracle: OpenSSL text output → expected verdict JSON |
| `make-cbom.mjs` | expected verdict JSON → CycloneDX 1.6 CBOM (reference output shape) |
| `certs/*.crt` | 11 self-signed certs, one per algorithm family/parameter set |
| `spki/*.spki.pem` | 12 public keys incl. ML-KEM-1024 (KEM keys have no cert form) |
| `expected/expected-classification.json` | the oracle output the product is tested against |
| `expected/sample-cbom.json` | schema-valid CycloneDX 1.6 document for the whole estate |

## The vectors

| certificate | signature alg | subject key | NIST category | CNSA 2.0 compliant |
|---|---|---|---|---|
| `rsa2048-sha256.crt` | sha256WithRSAEncryption | RSA-2048 | 0 (none) | no |
| `rsa3072-sha384.crt` | sha384WithRSAEncryption | RSA-3072 | 0 (none) | no |
| `rsa4096-sha512.crt` | sha512WithRSAEncryption | RSA-4096 | 0 (none) | no |
| `ec-p256-sha256.crt` | ecdsa-with-SHA256 | EC P-256 | 0 (none) | no |
| `ec-p384-sha384.crt` | ecdsa-with-SHA384 | EC P-384 | 0 (none) | no |
| `ed25519.crt` | ED25519 | Ed25519 | 0 (none) | no |
| `mldsa44.crt` | ML-DSA-44 | ML-DSA-44 | 2 | no (Level V required) |
| `mldsa65.crt` | ML-DSA-65 | ML-DSA-65 | 3 | no (Level V required) |
| `mldsa87.crt` | ML-DSA-87 | ML-DSA-87 | 5 | **yes** |
| `slhdsa-sha2-128s.crt` | SLH-DSA-SHA2-128s | SLH-DSA-SHA2-128s | 1 | no (not in CNSA 2.0 Table IV) |
| `slhdsa-shake-256f.crt` | SLH-DSA-SHAKE-256f | SLH-DSA-SHAKE-256f | 5 | no (not in CNSA 2.0 Table IV) |

The two SLH-DSA rows are deliberate traps: category 5 and quantum-resistant, yet **not**
CNSA 2.0-compliant because CNSA 2.0 Table IV lists only Kyber/Dilithium (for general
signatures) plus LMS/XMSS (for firmware). A product that equates "category 5" with
"CNSA compliant" fails on these two files.

## Key-length conformance (anti-substitution)

`expected-classification.json` records, for every SPKI, the BIT STRING key length measured from
the DER encoding and the value from the FIPS table. A file whose length does not match its OID
is a corrupted or mislabelled asset and must be reported as such, not silently classified.

| SPKI | octets measured | FIPS table | match |
|---|---|---|---|
| `mldsa44.spki.pem` | 1312 | 1312 (FIPS 204 Table 2) | yes |
| `mldsa65.spki.pem` | 1952 | 1952 | yes |
| `mldsa87.spki.pem` | 2592 | 2592 | yes |
| `mlkem1024.spki.pem` | 1568 | 1568 (FIPS 203 Table 3) | yes |
| `slhdsa-sha2-128s.spki.pem` | 32 | 32 (FIPS 205 Table 2) | yes |
| `slhdsa-shake-256f.spki.pem` | 64 | 64 | yes |

## Reproduce

```
$ cd golden-vectors && ./generate.sh                       # certs + spki (needs OpenSSL >= 3.5)
$ node derive-expected.mjs                                  # -> expected/expected-classification.json
$ node make-cbom.mjs                                        # -> expected/sample-cbom.json
    jsonschema.validate(json.load(open('expected/sample-cbom.json')), \
    json.load(open('../brief/references/cyclonedx-bom-1.6.schema.json'))); print('VALID')"
VALID
```

The committed `expected-classification.json` was produced this session and the `sample-cbom.json`
validates against the CycloneDX 1.6 schema (both commands pasted in the scout report). Each
component carries the certificate's real signature-algorithm OID (mapping table in
`make-cbom.mjs`), so a classical RSA-2048 asset shows `1.2.840.113549.1.1.11`, not a PQ OID.


These vectors test **classification**, not cryptographic operations. Nothing here validates an
ML-KEM/ML-DSA implementation: the signatures were made (or verified) by OpenSSL, and the product
under test never needs to verify them. Conformance claims about our own code stop at "parses and
classifies these certificates correctly".
